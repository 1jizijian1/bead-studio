## 踩的坑 & 怎么解的

### 坑 1：测试数据用了「不存在的颜色」

`exclude` 的单测一开始用 `#FF0000` / `#0000FF` 造数据，结果全挂。
排查发现：**纯红纯蓝根本不在那 291 色板里**（最近的是 `#FC283C` / `#324BCA`）。
而排除颜色的重映射白名单是「初始网格出现过的 hex」，这些 hex 必然来自调色板。
→ 结论：**是测试数据错了，不是代码错了**。改用 `findClosestDirect` 找真实色板 hex 再测。
教训：造测试数据要用真实数据域里的值。

### 坑 2：按计划做的性能优化（LUT 查表）实测后**删掉了**

计划里写了「最近色查询改用 5-bit RGB 量化 LUT，把 2600 万次距离计算降到 0」。
真做出来一测：

| | 90000 次查询（300×300 最坏情况） |
|---|---|
| 直接搜索 | **65 ms** |
| LUT 建表 + 查询 | 47 ms |

只快 18ms，但量化会把 **291 个色号里的 13 个错配到极其相近的邻居色**
（如 `#F7F8A2` → `#EEFCA5`）。拼豆是要**按色号买豆子**的，错配是实打实的问题，
而且会导致结果和网页版对不上。

→ **弃用 LUT，改回直接搜索**：一样快、精确、代码简单。
教训：**优化要拿数据说话，别凭直觉**。预测的 1-3 秒实际是 65ms。

### 坑 3：颜色多的时候，采购清单区本身就超画布上限

给导出写尺寸 clamp 时，单测发现 N=300、60 色的场景下，格子缩到最小的 2px
仍然塞不进 1200px —— 因为**清单区自己就有 884px 高**（60 色 2 列 = 30 行）。
而且我的循环缩到底后**静默放弃了**，没报错。

→ 修法：格子缩到底后继续**加宽清单列数**（列越多行越少）来压高度。
另外那个「画到画布外」的检查是靠**假 canvas context 记录所有绘制坐标**测出来的，
不需要模拟器就能抓到排版越界 —— 这个手法值得保留。

### 坑 4：Node 测试抓不到的参数漏传

提交前复查代码时发现：`editor` 调 `planExport` 时**漏传了 `colorCount`**。
后果是清单区高度算成 0，但 `includeStats` 还是 true —— 绘制时清单会被画到画布外面。
Node 测试没抓到是因为测试自己传了参数，**测的是函数、不是调用点**。

→ 修法：兜底 `colorCount > 0 ? colorCount : 1`，并补了一条针对「漏传」的回归测试。
教训：**测试覆盖了函数逻辑，不等于覆盖了调用方**。移植类改动要专门看一眼所有调用点。

### 坑 5（最重要）：网页版的默认阈值会把照片毁掉

第一次在开发者工具里跑真实照片，出来是一团黑，完全认不出。

**定位过程**（没有猜，全用数据）：
1. 把结果截图和原图都拿 PNG 解出来量像素 → 结果里 **54% 落在最暗档**，原图只有 11.8%
2. 在 Node 里用**同一套算法**跑原图 → **完整复现**了同样的黑图
   → 证明是小程序 Canvas 采样没问题，问题在算法层
3. 扫了一遍阈值：

   | 阈值 | 合并后颜色数 | 结果 |
   |---|---|---|
   | 0 | 51 | 正常，明度分布和原图吻合 |
   | 8 | 13 | 好用的拼豆图纸 |
   | 15 | 8 | 开始塌 |
   | **30（网页版默认）** | **3** | **79% 是近黑色** |

4. 量化这个 30 在色板上意味着什么：

   - 色板里**相邻色号**的距离中位数只有 **2.68**
   - 「绿 vs 棕」= 10.9，「中棕 vs 浅米」= 32.3，「中棕 vs 深黑」= 33.5

   阈值 30 是相邻间距的 **11 倍** —— 等于把绿植并进棕色、浅米并进中棕。

→ **结论：网页版的默认值 30 是为「扁平色块的卡通图」调的，用在照片上必然塌。**
   这是原项目的问题，我们照抄了默认值所以也中招。

**修法**：
- 默认阈值 30 → **8**（约相邻间距的 3 倍，既能去重复色又不并掉可辨颜色）
- 滑块范围 100 → **40**（可用区间实测只有 0~20）
- **加了设置版本号迁移**（`SETTINGS_VERSION`）——不然已经跑过的机器存着 30，改默认值根本不起作用
- 补了回归测试：断言默认阈值必须落在「相邻间距中位数」和「绿 vs 棕的距离」之间

**意外收获**：这次对拍等于验证了**小程序的 Canvas 采样链路是通的**。
截图里 54% 暗部，按画面占比折算正好对应 Node 算出的 79%——
说明 `createOffscreenCanvas` + `drawImage` + `getImageData` 这条链路数据是对的。

**教训**：移植一个项目时，**照抄默认值也是一种照抄**。代码逻辑对不代表默认参数在你的场景里也对。

### 坑 6：图纸「脏」——README 描述过的算法，代码里根本没有

阈值修对之后能认出图了，但学员反馈「太粗糙、太脏」：满屏孤立的单格杂点。

翻回原仓库 README，发现它**描述过**一个专门解决这个的算法：

> 「使用 BFS 从未访问单元格出发，将相邻单元格聚合成连通区域，统一设置为区域内出现次数最多的色号」

**但代码里没有**。真实代码只做了「全局按频率归并颜色」，那种做法完全不看空间位置，
所以清不掉孤立的单格杂点 —— 而拼豆图纸干不干净，主要就看这一步。

→ 按文档描述把 `utils/cleanup.js` 实现了：按 4-连通找色块，小于 N 格的块并进周围主导色。
   实测最小色块 2 时清掉 477 个孤点，细节还在；调到 8 会把瀑布、建筑细节一起抹平。

**教训：README 描述的功能不存在，可能导致你漏掉一个关键步骤。**
这次是第二次栽在「文档与代码不符」上了（第一次是颜色合并根本不是 BFS）。
**移植时要把「文档说的」和「代码做的」当成两条线索分别追。**

### 坑 7：图纸偏灰 —— 查到最后是色板本身没有这个颜色（不是 bug）

清理干净后整体还是偏灰冷：原图平均 `(88,72,57)` R-B=31，结果 `(77,65,64)` R-B=13，**暖调掉了一半**。

一路排查（每一步都有数据）：
1. 采样没问题 —— 逐格「代表色」的平均值和原图一致（`tools/color-check.js`）
2. 是**色板映射**在抬高蓝色通道：平均 dB=+12.9
3. 试过给色度轴加权（w=1~4），**没用** —— 源色和灰色都是低色度，差的是色相方向
4. 直接算目标色的 Oklab 坐标：`L=0.414, C=0.032, h=65°`（一个**低色度**暖色）
   对比候选：
   - `#55514C` 灰：ΔL=0.023、ΔC=0.023 → 距离 3.26 **被选中**
   - `#6C372F` 砖红：ΔL=0.011、**ΔC=0.045** → 5.50
   - `#78524B` 暖褐：色度接近但 ΔL=0.064 → 7.15

→ **色板在「L≈0.41、h≈65°、C 介于 0.04~0.07」这一档是空的。**
   有灰（C=0.01）也有砖红（C=0.08），就是没有中间那个「闷褐」。距离公式没选错，是没有更好的选项。

**为什么 CIEDE2000 也救不了**：灰色的色相是未定义的，ΔH≈0，所以灰度只赔色度不赔色相，
数学上照样更近。原项目 roadmap 里写着要换成 CIEDE2000，换了对这个情况也没用。

**结论**：这是真实拼豆色板的固有限制 —— 色板按饱和的珠子配，照片是低饱和的。
**拼豆本来就适合做扁平色块的图（卡通、logo、像素画），不适合照片**。这个是产品定位问题，不是代码问题。

### 坑 8：第三次栽在「照抄默认值」上 —— 默认格子数太小

学员反馈「瀑布、神庙都看不到，只能看到个人」，让我**再通读一遍仓库**看是不是有算法没用上。

**通读结果：没有漏掉的算法。** 把 `page.tsx` 的函数清单拉出来逐个核对
（`pixelateImage` / `handleToggleExcludeColor` / `handleAutoRemoveBackground` /
`floodFillErase` / `handleColorReplace` / `handleMagnifierPixelEdit` …），
跟算法相关的全移植了；`processFile` 里也确认**没有锐化、没有对比度增强、没有上采样**，
网页版就是把原图原尺寸直接送进采样。搜 sharpen/contrast/enhance/锐化/增强 也是空。

**真正的原因是格子数 N。** 对比实验（同一张 1920×1080）：

| N | 总豆数 | 效果 |
|---|---|---|
| 100（网页版默认） | 5,600 | 一格盖 19×19 像素，瀑布/神庙被平均掉 |
| 200 | 22,600 | 瀑布、神庙、岩壁纹理都出来了 |
| 300 | 50,700 | 接近像素画 |

网页版上传后也是重置成 100，我照抄了 → 又一次「照抄默认值」栽跟头
（前两次：合并阈值 30、以及默认参数没做迁移）。

→ 默认改成 **300**（学员要求先看最精细的效果），并把 `SETTINGS_VERSION` 提到 3
   让老用户能吃到新默认值。

**顺带修的两件事**：
- N=300 时导出每格只剩约 9px，格内色号写不下会自动省略。原来会**静默省略**，
  用户会以为导出坏了 —— 加了导出前的提示弹窗。
- 缩放为 1 时拖动不会改变视图，但每帧都在重绘五万格 —— 判断视图没变就跳过重绘。

**性能实测**（N=300，50700 格）：像素化 109ms + 合并 7ms + 杂色清理 21ms = **139ms**，可以接受。

**教训（第三次了，得记牢）**：**移植时「代码逻辑」「默认参数」「设置迁移」是三件独立的事。**
逻辑对不等于默认值合适，改了默认值还得管老用户的存量数据。

### 改成「成品尺寸」导向

原来滑块写的是「横轴格子数」—— 这是程序员的语言。拼豆的人想的是「我要拼多大、用几块板」。
所以把参数改成：

- **豆子尺寸**：5mm 标准 / 2.6mm 迷你（同一尺寸下迷你豆格子翻倍、成品更精细）
- **成品宽度**：直接调 cm（5~150，上限随豆距变，避免顶到格子数上限）
- **实时读数**：`约 30.0 × 17.0 cm · 60 × 34 格 · 6 块板`
- **超过 20 块板会变黄提醒**：成品偏大，手工拼会很久
- 首页加了「选什么图效果好」的提示卡（卡通/logo/像素画 优于照片）

格子数变成**派生量**（`utils/size.js` 换算），设置里不再存 —— 所以 `SETTINGS_VERSION` 提到 v4，
老用户的存量设置会被迁移掉。

**新增两个开发期工具**（都不进小程序包）：
- `tools/check-wxml.js`：静态检查 WXML 模板引用的变量是否都在 Page 的 data 里。
  小程序跑不起来时「模板引用了不存在的字段」是常见坑，而这个不用模拟器就能提前抓出来。
- 尺寸换算的 6 条断言（含 1 块板/66 块板两个边界）

## 今天最有价值的一条经验（给以后的自己）

**移植一个项目时，「代码逻辑」「默认参数」「设置迁移」是三件独立的事。**

今天我三次栽在同一个坑上：
- 合并阈值照抄 30 → 照片被合并成一团黑
- 格子数照抄 100 → 瀑布神庙全丢
- 改了默认值忘了做设置迁移 → 老用户机器上存的旧值让改动完全失效

**代码逻辑对，不代表默认参数在你的场景里也对。**
而且**改了默认值必须管老用户的存量数据**，否则改了等于没改。

另一条：**文档描述的功能可能根本不存在。** 原仓库 README 写了「BFS 连通区域合并」，
代码里却没有 —— 那是让图纸「不脏」的关键一步，漏了就做不出能看的图纸。
